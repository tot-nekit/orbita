# Данные, доступ и восстановление

## Что защищено

Production требует SQLCipher 4 с отдельным случайным 256-битным ключом. Шифруются страницы всей базы, включая задачи, диалоги, настройки, сессии, outbox и квоты, а также WAL и резервные копии. Пароли дополнительно защищены scrypt: N=32768, r=8, p=3, уникальная соль. В базе находятся только хеши случайных сессионных токенов и кодов восстановления.

Сайт использует HttpOnly/SameSite cookie; в production также Secure. Смена или восстановление пароля отзывает старые сессии и заменяет код восстановления. Код показывается один раз; без пароля и кода приложение не восстанавливает доступ по почте или имени. Псевдоним не секрет и может быть известен другим людям.

Шифрование действует при хранении, не является сквозным. Владелец сервера с ключом может читать записи; код восстановления аккаунта не заменяет ключ всей базы. Провайдер хостинга видит сетевые метаданные. Приложение не включает рекламные трекеры и не требует почту или настоящее имя. Ограничение частоты хранит HMAC сетевого адреса вместо исходного IP; сервер и внешний proxy могут обрабатывать IP при соединении.

AI для новых аккаунтов выключен. Включение разрешает передачу запроса и нужного контекста провайдеру. Telegram и браузерное/серверное распознавание речи находятся за пределами этого хранилища. У внешних сервисов собственные политики. Пользовательский JSON/CSV-экспорт содержит открытый текст по явному запросу пользователя.

## Ключи

DATABASE_KEY — 32 случайных байта, закодированных в base64url. Альтернатива для локальной установки — DATABASE_KEY_FILE с путём к приватному файлу. APP_SESSION_SECRET — другой постоянный секрет длиной от 32 символов для Telegram HMAC. Эти значения нельзя заменять одной и той же строкой.

Создать новый ключ, не выводя его в терминал:

```sh
python -m scripts.manage keygen --output data/.database_key
```

Команда не перезаписывает существующий файл. Скопируй ключ в отдельное защищённое хранилище, а не в Git или архив проекта. Без исходного ключа база и её копии не читаются. Изменение переменной окружения не выполняет ротацию ключа существующей базы. Защита диска не защищает ключ, лежащий рядом с ним, от полного захвата работающего сервера; для этого ключ хранится отдельно в секретах хостинга.

## Перенос прежней базы

1. Останови сайт, бота и launcher. Зафиксируй путь исходной базы и действующие настройки. Сохрани безопасную резервную копию; рабочую SQLite не копируют отдельно от её WAL.
2. Создай новый ключ и установи DATABASE_KEY_FILE либо DATABASE_KEY. Не помещай значение в аргументы команд, историю shell или чат.
3. Установи зависимости из requirements.txt и создай новый зашифрованный файл:

```sh
DATABASE_KEY_FILE=data/.database_key python -m scripts.manage encrypt --source data/orbita.sqlite3 --output data/orbita-encrypted.sqlite3
```

Команда использует SQLCipher export, проверяет целостность и количество строк всех таблиц. Исходная база остаётся на месте, существующий файл назначения не перезаписывается.

4. Укажи новый DATABASE_PATH, DATABASE_ENCRYPTION=1 и AUTH_REQUIRED=1 в секретах. Для локального HTTP: APP_ENV=local и COOKIE_SECURE=0. Для публикации нужны HTTPS, production и Secure cookie.
5. Запусти сервер и проверь данные правильным ключом. До удаления исходника создай и проверь зашифрованную резервную копию, сохрани ключ отдельно. Остаточные исходные файлы и старые копии без шифрования также нуждаются в защите; приложение не обещает их автоматическое стирание.

Старые общие web-записи не получает первый зарегистрировавшийся пользователь. После регистрации владелец сервера может явно перенести их в нужный аккаунт локальной командой:

```sh
python -m scripts.manage adopt-legacy --username YOUR_ALIAS --confirm
```

Это операция администратора с доступом к базе, не публичный API. При конфликте идентификаторов диалога перенос отменяется транзакционно. Telegram связывается только по одноразовому коду из своего бота, с явным подтверждением переноса.

## Копии и удаление

Копирование использует online backup API SQLCipher и тот же ключ. Копия проверяется и повторно открывается перед публикацией. По умолчанию создаются копии раз в 6 часов, сохраняются 28 последних: около недели при непрерывной работе. Копии на том же диске не защищают от потери диска; нужна отдельная защищённая внешняя копия.

Удаление одной записи мягкое, с восстановлением в течение 10 минут; запись остаётся в зашифрованной базе до обслуживания. Удаление аккаунта удаляет его записи, историю, настройки, привязки и активные сессии из рабочей базы. Старые резервные копии содержат прежнее состояние до ротации. Ранее отправленные сообщения Telegram, пользовательские экспорты и данные у AI-провайдера приложение отозвать не может.

Восстановление делается на отдельном пути: открытие SQLCipher правильным ключом, integrity_check, сверка ожидаемых записей. Замена рабочей базы — только после остановки всех процессов; прежнюю базу сохраняют для отката. Не восстанавливай копию поверх активной SQLite.

Внешний независимый аудит безопасности не проводился. Тесты проверяют конкретные сценарии и не дают гарантии отсутствия всех уязвимостей.
